# Grafana as a capability

By adding Grafana as a capability all Paas requestors can also enable the `grafana` capability,
and get their very own Grafana to monitor all resources belonging to their Paas.

## Prerequisites

- Make sure K8s, ArgoCD and the Paas operator are [installed properly](../../README.md)
- Install the grafana operator:
  ```
  kubectl create -f https://github.com/grafana/grafana-operator/releases/latest/download/kustomize-cluster_scoped.yaml
  ```
- Provide the settings listed in [Settings you must provide](#settings-you-must-provide),
  most importantly the `grafana-proxy` session secret.
- Install the extra resources as required by the Paas Capability integration
  ```
  kubectl apply -k ./deploy
  ```

## Settings you must provide

This capability is an example to take inspiration from, not a ready-to-run production setup.
Some settings are deliberately left out of this repository because they must be unique and secret
for every installation. Copying the manifests as-is will not give you a working Grafana until
you provide them.

| Setting | Where | Why |
|---------|-------|-----|
| `session_secret` in Secret `grafana-proxy` | Every namespace that runs a Grafana instance | Signs and encrypts the oauth-proxy session cookie. Anyone who knows it can forge a session. See [Session secret](#session-secret). |
| Grafana admin credentials | Generated by the grafana-operator in Secret `grafana-paas-admin-credentials` | Do not set `security.admin_password` in [the Grafana resource](./deploy/g_grafana-deployment.yaml). A static password in a template is known to everyone who reads it. If you need fixed credentials, set `GF_SECURITY_ADMIN_USER`/`GF_SECURITY_ADMIN_PASSWORD` on the grafana container in `spec.deployment` with `valueFrom.secretKeyRef` pointing to your own Secret. |
| Default role for new users (`users.auto_assign_org_role`) | [Grafana resource](./deploy/g_grafana-deployment.yaml) | Every user who passes the oauth-proxy is created with this role. The template uses `Viewer`. Grant `Editor` or `Admin` explicitly (for example with team sync or the Grafana API) rather than raising the default. |
| `users.editors_can_admin` | [Grafana resource](./deploy/g_grafana-deployment.yaml) | `false` in the template. Only enable it when editors must manage teams and folders. |
| Login form (`auth.disable_login_form`) | [Grafana resource](./deploy/g_grafana-deployment.yaml) | Disabled in the template: users log in through the oauth-proxy. Basic auth stays enabled because the grafana-operator uses it. |

### Session secret

The oauth-proxy sidecar reads its cookie secret from `/etc/proxy/secrets/session_secret`,
mounted from the Secret `grafana-proxy`. Rules for this value:

- Generate a random value of 16, 24 or 32 bytes per Grafana instance, never shared between
  namespaces or clusters.
- Never commit the value to git, not even to a private repository.
- Rotate the value when it may have leaked. Restart the Grafana pods afterwards; existing sessions
  become invalid and users log in again.

Create the Secret manually:

```
kubectl -n <paas>-grafana create secret generic grafana-proxy \
  --from-literal=session_secret="$(openssl rand -base64 24)"
```

`openssl rand -base64 24` produces exactly 32 characters, which the oauth-proxy accepts as an AES-256 key.

When Grafana is rolled out per Paas, creating the Secret by hand does not scale. Automate it
instead, for example with:

- the [External Secrets Operator](https://external-secrets.io/) `Password` generator combined
  with an `ExternalSecret`, which creates a random value per namespace;
- your own secret management (Vault, Sealed Secrets, ...), as long as every instance gets its own value.

Do not generate the value with Helm functions such as `randAlphaNum`. ArgoCD renders the chart
on every sync, so the secret would change on each sync and log out all users.

## Adding Grafana as a capability

### Paas Config changes

Add the following to your Paas config block:

```yaml
apiVersion: cpet.belastingdienst.nl/v1alpha2
kind: PaasConfig
metadata:
  name: paas-config
...
spec:
  capabilities:
    grafana:
      custom_fields:
        image:
          validation: ^ghcr.io/myorg/something.*$
      default_permissions:
        grafana-paas-sa:
        - cluster-monitoring-view
      quotas:
        clusterwide: false
        defaults:
          limits.memory: 2Gi
          requests.cpu: "1"
          requests.memory: 1Gi
        ratio: 0
```

This would enable a capability called grafana, which means:
- that the plugin generator will respond to a request for Paas'es with the grafana capability enabled.
  The Paas can have `custom_fields` as defined in the `custom_fields` for the `grafana` capability in the PaasConfig.
  The plugin generator will have these values (either input in the Paas, or a templated value using go-templating as defined in the PaasConfig) as key/value pairs in the response.
- Furthermore, for every paas with an enabled grafana capability, a namespace and cluster quota is created.

### Applicationset

For integration with ArgoCD, there needs to be an ApplicationSet with plugin generator generator configuration.
Use [this example](./applicationset.yaml) and change to your needs.
